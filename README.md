# Independent security health monitor

This standard-library Python monitor runs from GitHub-hosted Actions and checks one configured HTTPS health publication every half-hour, at minutes 7 and 37. It has no SSH, advertising, browser or business integration credentials. Scheduled Actions are best-effort and can be delayed. This is not a real-time intrusion detector.

This repository publishes generic source code. Issues and Actions logs also expose generic healthy/unhealthy transitions and timestamps. The endpoint URL, Telegram bot credential and recipient are private GitHub Actions secrets named `HEALTH_URL`, `ALERT_BOT_TOKEN` and `ALERT_CHAT_ID`. Do not put their values in repository files, issue bodies, dispatch inputs or logs. No client names or advertising-account identifiers belong here. The configured endpoint must use HTTPS on port 443 with exact path `/security-health.json`; redirects, query strings, fragments and embedded credentials are rejected.

The health response is limited to 4096 bytes with a ten-second total network deadline. Its only fields are `schema_version`, `generated_at_utc`, `ok` and `checks`. All five named checks must be booleans and true, the top-level status must agree, and publication age must be between 60 seconds in the future and 300 seconds in the past. Unexpected fields and duplicate JSON keys fail validation.

The repository owner provisions two state issues titled `Security monitor state: production` and `Security monitor state: test`, with initial JSON from `monitor.new_state("production")` and `monitor.new_state("test")`. Their exact numbers must be set as repository variables `PRODUCTION_STATE_ISSUE_ID` and `TEST_STATE_ISSUE_ID`. The monitor reads only those IDs and verifies the exact title, number and owner or github-actions bot author. It never discovers state by public issue titles, creates state issues or reads issue comments. Unrelated public issues cannot substitute state. No endpoint, account name, token, chat ID or service data is stored there. Do not delete or manually edit these state issues during normal operation.

Before sending, the monitor durably writes a `claimed` notification transition and reads it back. After a verified Telegram receipt it writes `sent`. A request error or invalid receipt becomes `unknown`. An unresolved `claimed` or `unknown` delivery blocks automatic notification retries and fails the workflow. This prevents duplicate sends after an uncertain response. The operator must inspect the actual Telegram history and reconcile the one issue state before resuming notifications. Do not mark an uncertain notification sent without checking. A failed run is visible in Actions even if Telegram fails.

The first healthy production check establishes a baseline without a message. A change to unhealthy sends one alert; unchanged failure does not send repeated Telegram messages. A change back to healthy sends one recovery message. Manual dispatch modes `failure` then `recovery` exercise TEST alerts without stopping or changing any monitored service. Both messages are clearly labelled TEST ONLY.

The health workflow permissions are `contents: read` and `issues: write`. It downloads only this repository's `monitor.py` at the exact workflow commit through GitHub's authenticated API, with no third-party action. A concurrency group serializes runs. The job cap is one minute. GitHub and Telegram calls have five-second total deadlines; the health call has a ten-second total deadline. No Python packages are installed. At two runs per hour, a 30-day month has about 1,440 scheduled checks. Standard GitHub-hosted runners are free for this public repository; private-repository charges would depend on the plan and shared allowance.

A separate weekly maintenance workflow has only `contents: write`, receives no alert secrets, and changes the fixed `monitor-activity.json` file once per UTC month. It reads its code from the exact workflow commit and verifies the resulting file after writing. An uncertain write is reconciled by reading the file on the next run, never by blindly replaying a commit. This supplies regular repository activity to reduce the risk of GitHub's 60-day inactivity disablement. It is a mitigation, not a scheduler guarantee. It neither edits health state nor sends messages.

Local tests: `python3 -m unittest -v test_monitor test_maintain`. Tests use mocked transports and do not contact GitHub, Telegram or a production endpoint.

Before activation, install the three secrets, provision the two owner-authored state issues and exact ID variables, inspect the deployed workflow/source, execute failure and recovery TEST dispatches, verify the actual Telegram recipient and messages, then verify a production check and the installed schedules. Publish the workflows only after secrets and state are ready. A source-controlled schedule alone does not prove that GitHub will run it. Review actual run history and account notifications. Existing GitHub administrators can change or disable this monitor, so it is independent of host uptime, not independent of that account's administrative authority.

References: [GitHub workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax), [GitHub Issues API](https://docs.github.com/en/rest/issues/issues), [Telegram sendMessage](https://core.telegram.org/bots/api#sendmessage).
